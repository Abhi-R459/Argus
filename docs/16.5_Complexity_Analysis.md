# Section 16.5 — Complexity Analysis

## 1. Asymptotic Summary

The following table summarizes the time and space complexity of Argus's core operations relative to the total number of historical audit records ($N$), the number of records since the latest signed checkpoint ($k$), the number of CPU worker processes ($P$), the number of checkpoint segments ($S$), and the number of historical versions for a single entity ($m$):

| Operation | Time Complexity | Auxiliary Space Complexity | Dominant Cost Factor |
|---|---|---|---|
| **Audited Write (Insert/Update/Delete)** | $O(1)$ amortized marginal overhead | $O(1)$ per row | Row-lock contention on `chain_state` |
| **Index Maintenance (Baseline DB)** | $O(\log N)$ | $O(\log N)$ | B-tree balance on `idx_audit_log_seq_time` |
| **Sequential Verification Walk** | $O(N)$ | $O(1)$ | Keyset-paginated I/O and SHA-256 compute |
| **Checkpoint-Resumed Verification** | $O(k)$ ($k \ll N$) | $O(1)$ | Scan from checkpoint boundary $s_{cp}$ |
| **Parallel Segment Verification** | $O\left(\frac{N}{P} + S\right)$ | $O(P \cdot B)$ ($B = \text{page size}$) | Process pool dispatch & boundary check |
| **Historical State Reconstruction** | $O(\log N + m)$ | $O(m)$ | Index seek + JSONB delta merge |
| **Counterfactual Provenance Replay** | $O(\log N + m)$ | $O(m)$ | In-memory JSONB delta merge with skip set |
| **Merkle Tree Construction ($K$ items)** | $O(K)$ | $O(K)$ | RFC 6962 SHA-256 bottom-up reduction |
| **Merkle Audit Path Proof Extraction** | $O(\log K)$ | $O(\log K)$ | Sibling hash extraction |
| **Merkle Proof Verification (Air-Gapped)** | $O(\log K)$ | $O(1)$ | $\lceil \log_2 K \rceil$ SHA-256 hash folds |
| **Multi-Witness Quorum Check ($W$ witnesses)** | $O(W) = O(1)$ | $O(1)$ | Threshold Ed25519 signature verification |
| **External Checkpoint Push** | $O(1)$ | $O(1)$ | HTTP network round-trip & Ed25519 signing |

## 2. Write-Path Overhead & Index Maintenance

### 2.1 Amortized $O(1)$ Marginal Cost
Every mutation on an audited table triggers Algorithm 1. The algorithmic components of this write are:
1. **Lock Acquisition:** `SELECT tail_hash FROM chain_state WHERE id = 1 FOR UPDATE`. This is an index scan on a 1-row primary key table ($O(1)$).
2. **Payload Serialization:** Masking PII and serializing fields into a canonical UTF-8 string. Because schema widths and JSON payloads are bounded by constant upper bounds ($C_{bytes} < 4\text{ KB}$), this operation is strictly $O(1)$.
3. **Cryptographic Hashing:** Computing $\text{SHA256}(S(R_i) \parallel H_{i-1})$ executes in $O(1)$ time on fixed-length block buffers.
4. **Append to `audit_log`:** Appending a row to the heap table executes in $O(1)$ I/O page time.

Thus, the marginal algorithmic overhead added by the Argus tamper-evident trigger is strictly **$O(1)$** per transaction, independent of the volume of records already stored in `audit_log`.

### 2.2 Distinction from Relational Index Maintenance
It is essential to distinguish the audit trigger's $O(1)$ marginal overhead from the database engine's underlying index maintenance. The `audit_log` table maintains two primary B-tree indexes:
- `idx_audit_log_seq_time` on `(sequence_id, created_at)`
- `idx_audit_log_employee_time` on `(row_id, created_at)` WHERE `table_name = 'employees'`

Every relational database insert incurs an $O(\log N)$ tree balancing traversal per index. While this introduces an $O(\log N)$ cost component, this is a standard relational indexing property shared by all enterprise database systems, not an artifact of cryptographic hash chaining.

## 3. Verification Engine Complexity

### 3.1 Sequential Verification: $O(N)$ Time, $O(1)$ Memory
A naive verification implementation using standard `OFFSET` pagination incurs severe quadratic degradation:
$$\sum_{j=1}^{N/B} O(j \cdot B) = O(N^2)$$
Argus eliminates this degradation through **keyset pagination** (Decision #9):
```sql
SELECT * FROM audit_log WHERE sequence_id > :last_seen_seq ORDER BY sequence_id LIMIT :page_size;
```
Because `sequence_id` is indexed via a B-tree, advancing the cursor takes $O(\log N)$ for the initial page seek, followed by $O(B)$ sequential page scans. For a total chain length $N$ divided into pages of size $B = 500$, the total retrieval time is:
$$T_{seq}(N) = \frac{N}{B} \cdot O(B) = O(N)$$
Furthermore, by streaming batches into a generator that retains only the preceding entry's hash in memory, auxiliary heap memory remains strictly bounded:
$$M_{seq} = O(B) = O(1)$$

### 3.2 Checkpoint-Resumed Verification: $O(k)$
When verification resumes from the latest verified and externally anchored checkpoint at sequence $s_{cp}$, the verifier skips historical rows $1 \dots s_{cp}$:
$$T_{resumed} = O(N - s_{cp}) = O(k)$$
Under typical operating conditions where checkpoints occur every $C = 1,000$ operations, audit verification executes in sub-second time ($k \le 1,000$) regardless of whether total audit history spans millions of records.

### 3.3 Parallel Segment Verification: $O(N/P + S)$
In parallel verification mode (Algorithm 3), the chain is divided across $S$ checkpoint intervals and assigned to a pool of $P$ worker processes (`ProcessPoolExecutor`).

Let $T_w$ represent the wall-clock execution time. By Amdahl's Law, the parallel execution satisfies:
$$T_{parallel}(N, P, S) = \max_{j \in \{1 \dots S\}} T(\text{segment}_j) + T_{reconcile}(S)$$

Assuming balanced checkpoint intervals of size $L = N / S$:
$$T_{parallel} \approx \frac{N}{P \cdot \mu} + O(S)$$
where $\mu$ is the single-core verification throughput (empirically measured at $\approx 8,500$ entries/second), and $O(S)$ represents the sequential post-pass where the parent process queries $S-1$ boundary rows to verify cross-segment continuity (Decision #15).

When $N \gg S$, the $O(S)$ boundary term is negligible, yielding near-linear speedup with core count:
$$\text{Speedup}(P) = \frac{T_{sequential}}{T_{parallel}} \approx \frac{P}{1 + P \cdot \frac{S \cdot t_{boundary}}{N}}$$

## 4. Historical State Reconstruction Complexity (DB-018)

The stored routine `reconstruct_employee_state(p_employee_id, p_as_of)` reconstructs the state of an employee at an arbitrary point in historical time $\tau$:
```sql
SELECT action, old_value, new_value 
FROM audit_log 
WHERE table_name = 'employees' AND row_id = p_employee_id AND created_at <= p_as_of
ORDER BY sequence_id ASC;
```

### Analysis
1. **Index Seek:** The composite index `idx_audit_log_employee_time` enables a direct B-tree range scan for the given `row_id` in $O(\log N)$ time.
2. **Replay Loop:** Let $m$ be the number of updates recorded for that specific employee prior to $\tau$ ($m \ll N$, typically $m < 50$). The PL/pgSQL function iterates over $m$ rows, merging JSONB deltas via `v_state || new_value`.
3. **Total Complexity:**
   $$T_{reconstruct} = O(\log N + m)$$

Without the composite index, this query would degrade to a full table scan ($O(N)$). With the index, reconstruction latency remains under 5 milliseconds even at $N = 100,000$.

## 5. Storage Space Expansion Factor

We model the storage consumption of Argus relative to raw relational rows:

1. **Raw Table Row:** A typical `employees` row occupies $\approx 180\text{ bytes}$.
2. **Audit Log Row:** An `audit_log` row contains:
   - Fixed headers: `sequence_id` (8B), `actor_user_id` (8B), `action` (8B enum), `table_name` (16B), `row_id` (8B), `severity` (8B), `created_at` (8B) $\approx 64\text{ bytes}$.
   - Cryptographic fields: `entry_hash` (64B hex), `previous_hash` (64B hex) $= 128\text{ bytes}$.
   - JSONB Payloads: `old_value` + `new_value` with masked PII $\approx 220\text{ bytes}$.
   - Total per audit record: $\approx 412\text{ bytes}$.
3. **Storage Expansion Ratio:**
   $$\alpha = \frac{\text{Size}(\text{audit\_log})}{\text{Size}(\text{employees})} \approx 2.29\times$$
4. **Checkpoint Footprint:** Each checkpoint consumes only 1 row in `chain_checkpoints` ($\approx 160\text{ bytes}$) per 25–1,000 transactions. The checkpoint storage overhead is less than $0.1\%$ of the total audit log volume.

## 6. Phase 13 Cryptographic Frontiers Complexity Analysis

### 6.1 Selective Merkle Tree & Inclusion Proof Complexity (NOVEL-009)
Let $K$ denote the number of audit log entries sealed within a single checkpoint interval $[S_{\text{start}}, S_{\text{end}}]$.
1. **Tree Construction:** Computing $K$ leaf digests with prefix `0x00` requires $K$ invocations of SHA-256. Building the intermediate layers with prefix `0x01` and odd-leaf promotion requires $\sum_{j=1}^{\lceil \log_2 K \rceil} \lceil K / 2^j \rceil < K$ SHA-256 operations. Thus, total construction time is strictly $O(K)$, executing in $\approx 0.12\text{ ms}$ for $K = 25$ and $< 3\text{ ms}$ for $K = 1,000$.
2. **Proof Size:** A Merkle audit path consists of exactly $\lceil \log_2 K \rceil$ sibling hash objects (`direction` + 32-byte hash). For $K = 25$, proof length is at most 5 hashes ($\approx 320\text{ bytes}$ JSON). For $K = 1,000,000$, proof length is only 20 hashes ($\approx 1.28\text{ KB}$).
3. **Air-Gapped Verification:** A client or regulator verifying an inclusion proof folds $\lceil \log_2 K \rceil$ hashes from leaf to root. Verification time is $O(\log K)$, executing in $< 0.05\text{ ms}$ in pure Python without database connections.

### 6.2 Counterfactual Provenance Replay Complexity (NOVEL-011)
Replaying the provenance of an entity across $m$ historical modifications while excising a subset of contested sequences:
1. **Index Seek:** B-tree range scan on `(row_id, created_at)` executes in $O(\log N)$ time.
2. **Replay Loop:** Filtering $m$ rows against an in-memory hash set of skip IDs takes $O(1)$ per row. In-memory JSONB delta merging executes in $O(m)$ time.
3. **Blast Radius Math:** Single pass scalar subtraction on numerical compensation attributes takes $O(1)$ time.
4. **Total Complexity:** $T_{\text{counterfactual}} = O(\log N + m)$. For typical entity histories ($m \le 100$), simulation completes in under 4 milliseconds.

### 6.3 Multi-Witness Quorum Complexity (NOVEL-010)
Verifying an RFC 9162 witnessed checkpoint involves validating $W$ witness signatures against the registered public keys:
1. **Signature Checks:** Verifying each Ed25519 signature takes $O(1)$ constant time ($\approx 0.25\text{ ms}$ per signature using `cryptography` OpenSSL backend, or $\approx 4\text{ ms}$ in pure Python).
2. **Threshold Quorum:** Comparing the count of valid distinct witness signatures against the quorum threshold $M$ (e.g., $M = 2$ of $W = 3$) requires $O(W)$ set operations. Because $W \ll 10$, total quorum verification is strictly $O(1)$ and executes in $< 1\text{ ms}$.
