# Section 16.2 — Threat Model

## 1. Overview & System Context

Argus is a tamper-evident audit logging and verification engine built natively into PostgreSQL. In enterprise systems managing sensitive data—such as payroll, compensation histories, and identity records—audit trails are critical for compliance, forensic investigation, and regulatory assurance. Traditional relational audit trails (e.g., table change logs, shadow tables, or trigger-based capture) store audit events as mutable rows within the same database engine. While this model protects against unauthorized standard users via Discretionary Access Control (DAC), it is fundamentally vulnerable to insider threats and administrative compromise: any database superuser (or an attacker who attains superuser credentials via credential theft, SQL injection, or misconfiguration) can silently execute `UPDATE` or `DELETE` statements against the audit log, rewriting or excising historical transactions without detection.

Argus solves this vulnerability through a three-tier defense-in-depth model:
1. **Tier 1 (In-Engine Cryptographic Hash Chaining):** Atomic `AFTER` triggers compute a cryptographic hash over each row modification linked to the previous state, enforced by strict row-level serialization via `SELECT ... FOR UPDATE` on a singleton state table.
2. **Tier 2 (Signed Checkpoints):** A standalone, out-of-process verification agent periodically aggregates hash ranges into checkpoints and signs them using an asymmetric Ed25519 private key inaccessible to the database engine.
3. **Tier 3 (External Anchoring):** Signed checkpoints are published to an independent, external append-only store (e.g., a private GitHub repository or WORM storage) that superusers cannot manipulate.

## 2. Threat Actors & Capabilities

We formalize the adversary capabilities using a tiered threat actor taxonomy:

### Threat Actor 1: Rogue Database Administrator (DBA) / Compromised Superuser ($A_{DBA}$)
- **Privilege Level:** PostgreSQL `postgres` superuser or `rds_superuser`.
- **Capabilities:**
  - Can connect directly via `psql` or native socket, bypassing all application-level logic.
  - Can bypass table-level permissions (`REVOKE UPDATE, DELETE ON audit_log`).
  - Can disable or drop triggers temporarily (`ALTER TABLE ... DISABLE TRIGGER`).
  - Can directly manipulate table storage via raw SQL statements (`UPDATE audit_log`, `DELETE FROM audit_log`).
  - Can stop, restart, or inspect PostgreSQL database clusters and write-ahead logs (WAL).
- **Limitations:**
  - Cannot access the file system of the external verifier machine or the verifier's environment where the Ed25519 private signing key resides.
  - Cannot alter commits or pull requests on the external anchor store (e.g., GitHub repository) due to external IAM and multifactor authentication boundaries.

### Threat Actor 2: Compromised Application Layer ($A_{APP}$)
- **Privilege Level:** Web application service account (e.g., FastAPI backend connecting as `hr_admin` or `app_user`).
- **Capabilities:**
  - Can issue arbitrary SQL queries permitted to the application role.
  - Can attempt unauthorized employee creation, salary alterations, or identity changes.
  - Can attempt to forge session-level variables (such as `argus.actor_user_id` or `argus.actor_employee_id`).
- **Limitations:**
  - Bound by PostgreSQL Discretionary Access Control (`REVOKE UPDATE, DELETE ON audit_log`).
  - Cannot modify the audit log directly.
  - Cannot alter the PL/pgSQL trigger definitions or stored procedures.

### Threat Actor 3: Malicious Insider / Unprivileged Employee ($A_{USER}$)
- **Privilege Level:** Authenticated end-user (e.g., regular HR specialist or standard employee).
- **Capabilities:**
  - Authenticated via application auth (e.g., Clerk JWT).
  - Can submit HTTP requests to API endpoints.
- **Limitations:**
  - Completely restricted from direct database access.
  - Subject to business rule validation enforced both in application logic and in database triggers (e.g., self-salary modification blocks, salary drop limits).

### Threat Actor 4: External Network Adversary ($A_{NET}$)
- **Privilege Level:** Zero initial credentials; remote network presence.
- **Capabilities:**
  - Eavesdropping on unencrypted traffic, man-in-the-middle (MITM) attempts, credential spraying, injection attempts.
- **Limitations:**
  - Bound by network firewalls, TLS 1.3 encryption, and database authentication.

## 3. Trust Assumptions & Security Perimeters

Argus operates under a rigorous set of stated trust assumptions:

1. **Cryptographic Primitives:** The SHA-256 collision resistance and preimage resistance assumptions hold. The Ed25519 signature scheme is unforgeable under chosen message attacks (EUF-CMA).
2. **PostgreSQL Relational Engine Integrity:** The PostgreSQL query planner, transaction engine, and Write-Ahead Logging (WAL) operate correctly according to ACID semantics. Database triggers execute deterministically and atomically within the caller's transaction.
3. **Verifier Host Isolation:** The verification engine runs on an isolated host or administrative container distinct from the database server. The Ed25519 private key (`argus_private.pem`) is stored locally on the verifier host with restrictive permissions (`0600`) and is never loaded into database memory, environment variables, or client web browsers.
4. **Anchor Store Independence:** The external anchoring target (e.g., GitHub repository via personal access token or WORM storage) maintains independent authentication, audit logs, and versioning. Compromise of the PostgreSQL instance does not grant write access to the anchor store's historical commitments.

## 4. Attack Surfaces & Vector Analysis

The system exposes five primary attack surfaces:

```
                  ┌─────────────────────────────────────────────────┐
                  │                 External Store                  │
                  │              (GitHub / Anchors)                 │
                  └──────────────────────▲──────────────────────────┘
                                         │ Push Signed Checkpoint
                                         │ (EUF-CMA Ed25519)
┌───────────────────────────────┐        │
│      Verification Engine      ├────────┘
│    (Independent Python CLI)   │
│ - Reads audit_log via keyset  │
│ - Signs with ~/.argus/*.pem   │
└───────────────▲───────────────┘
                │ Read-only SQL
                │
┌───────────────▼───────────────────────────────────────────────────┐
│                     PostgreSQL Database Engine                    │
│                                                                   │
│  [Surface 1: Direct SQL]   <── Rogue DBA / Superuser (psql)       │
│  [Surface 2: App Sessions] <── Compromised API Backend (FastAPI)  │
│  [Surface 3: Storage Files]<── Filesystem / Backup Dump Attacks   │
│                                                                   │
│  Tables:                                                          │
│   - employees, salary_history (Trigger-protected)                 │
│   - audit_log (Append-only via REVOKE)                            │
│   - chain_state (Serialized via SELECT ... FOR UPDATE)            │
│   - chain_checkpoints (Signed checkpoints)                        │
└───────────────────────────────────────────────────────────────────┘
```

1. **Direct SQL Console (Surface 1):** Attackers with superuser roles execute arbitrary DDL or DML against `audit_log`, `chain_state`, or data tables.
2. **Application Connection Pool (Surface 2):** Attackers hijack the application connection pool to issue unauthorized operations or forge audit metadata.
3. **Physical Storage & Backups (Surface 3):** Attackers modify raw PostgreSQL heap tables (`pg_data`) or tamper with database dumps generated via `pg_dump`.
4. **Verifier Execution Pipeline (Surface 4):** Attackers target the verifier process, attempting denial of service, memory corruption, or fake verification outputs.
5. **External Anchoring Interface (Surface 5):** Attackers intercept or inject falsified checkpoint files into the external repository.

## 5. Security Goals & Formal Guarantees

Argus guarantees the following security properties:

### 1. Forward Integrity
Once an audit record $R_i$ is committed and linked into the chain at sequence $i$, no prior record $R_j$ ($j \le i$) can be modified or deleted without:
- Invalidating the hash chain relation $H_k = \text{SHA256}(S(R_k) \parallel H_{k-1})$ for all $k > j$, OR
- Generating a hash collision on SHA-256.

### 2. Backward Integrity & Concurrency Safety
Every new entry $R_{i+1}$ must reference the exact current tail hash $H_i$ stored in `chain_state`. Because `chain_state` requires exclusive row locking (`SELECT id FROM chain_state WHERE id = 1 FOR UPDATE`), concurrent transactions cannot create branching forks, race conditions, or conflicting sequence IDs.

### 3. Non-Repudiation of Checkpoints
Every checkpoint generated by the verifier is signed with Ed25519:
$$\sigma = \text{Sign}_{sk}(H_{cp})$$
Even if a superuser rewrites the entire audit log table from sequence 1 to $N$ and recomputes valid contiguous hashes (the "recompute-and-hide" attack), the resulting hashes will not match the externally anchored, signed checkpoints. The attacker cannot forge a valid signature $\sigma'$ without the private key $sk$.

### 4. Zero-Leakage Audit Payloads
Personally Identifiable Information (PII) such as national identification numbers and direct contact details are encrypted at rest with `pgcrypto` (`national_id_encrypted`, `contact_info_encrypted`). When audit triggers record row snapshots, the `mask_employee_payload()` function deterministically strips sensitive byte buffers and substitutes the literal `[REDACTED]`. Consequently, compliance auditors inspecting `audit_log` gain full forensic visibility over operations without accessing plaintext PII.

## 6. Attack Comparison Matrix

The table below contrasts Argus against standard relational logging solutions (e.g., unchained shadow tables or `pgMemento`-style changelogs) across six threat scenarios:

| Attack Scenario | Naive Relational Audit Log | pgMemento / Trigger Log | Argus Architecture |
|---|---|---|---|
| **1. Historical Record Deletion** (`DELETE FROM audit_log WHERE id = k`) | Undetected. Sequence gaps easily concealed or ignored. | Undetected. Log row is removed without trace. | **Detected (Chain Break & Gap).** Verifier identifies missing sequence ID and broken hash link ($H_{k+1}.previous\_hash \ne H_{k-1}.entry\_hash$). |
| **2. In-Place Field Mutation** (`UPDATE audit_log SET new_value = ...`) | Undetected. Data permanently altered with no historical proof. | Undetected unless additional recursive triggers exist. | **Detected (Hash Mismatch).** Recomputed hash $H'_k \ne H_k$. Verifier flags tampered row. |
| **3. Recompute-and-Hide Attack** (Modify row $k$ and recompute all $H_{k..N}$) | Undetected. | Undetected. | **Detected (Anchor Mismatch).** New tail and intermediate hashes conflict with signed, externally anchored checkpoints. |
| **4. Checkpoint Tampering** (`DELETE FROM chain_checkpoints`) | N/A (No checkpoints exist). | N/A. | **Detected (Anchor Discrepancy).** Verifier detects missing checkpoint referenced by external anchor store. |
| **5. Anchor Forgery** (Plant fake checkpoint in GitHub store) | N/A. | N/A. | **Rejected (Invalid Signature).** Ed25519 signature verification fails; forged file discarded with forensic alert. |
| **6. App-Level Privilege Escalation** (Compromised HR Admin tries log edit) | Depends on application permissions; often succeeds. | Succeeds if app role has DML privileges. | **Blocked at Kernel.** PostgreSQL Discretionary Access Control (`REVOKE UPDATE, DELETE`) raises immediate permission denied exception. |

## 7. Out-of-Scope Threats & Limitations

To maintain academic honesty, the following scenarios are explicitly classified as out of scope:

1. **Complete Host / Hypervisor Subversion:** An attacker with root access to the physical host running both the PostgreSQL database and the verifier machine who can extract memory from the verifier process can obtain the Ed25519 private key. Argus requires host-level isolation for the verifier.
2. **Denial of Service (DoS):** A superuser can drop tables or terminate the PostgreSQL daemon. Argus guarantees *tamper-evidence*, not *high availability under intentional superuser sabotage*.
3. **Client Plaintext Compromise:** Plaintext compromise occurring before data reaches the database (e.g., keylogger on the HR administrator's workstation) cannot be rectified by database-tier auditing.
