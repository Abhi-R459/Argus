## 1. Executive Summary & Security Architecture

Argus adopts an integrated defense-in-depth posture centered on the classical **CIA Triad** (Confidentiality, Integrity, Availability). While traditional relational security controls focus almost exclusively on authorization (Discretionary Access Control), Argus incorporates cryptographic guarantees directly into database transactions, ensuring that data and audit histories remain tamper-evident, non-repudiable, and privacy-preserving.

## 2. Confidentiality Analysis

In human resources and enterprise systems, audit trails must not become vehicles for illicit data exfiltration. An audit log that uncritically records raw database rows violates privacy mandates (such as GDPR and state privacy statutes; noting that while HIPAA §164.312 mandates analogous controls, HIPAA specifically governs Protected Health Information) by exposing employee identifiers, tax numbers, and private compensation figures to auditors who only require forensic proof of transaction validity.

### 2.1 Storage-Tier Encryption (`pgcrypto`) & Module Boundary
Confidentiality for highly sensitive employee attributes is enforced at rest inside PostgreSQL using the native `pgcrypto` extension:
- `national_id_encrypted`: Stored as raw `BYTEA` encrypted via AES-256 (NIST FIPS 197).
- `contact_info_encrypted`: Stored as encrypted `BYTEA`.
Decryption keys are maintained outside the database engine in an external key management service (KMS) or application environment and are never stored in database tables or trigger parameters.

**Cryptographic Module Boundary Notice:** The PostgreSQL `pgcrypto` extension is an open-source software library and is **not** a NIST CMVP-validated cryptographic module under FIPS 140-2 / FIPS 140-3. Argus implements NIST-approved algorithms, but does not claim hardware- or module-level CMVP lab certification.

### 2.2 Deterministic Audit Payload Masking
When table mutations fire the audit triggers (`trg_audit_employees`), row images are processed through the stored routine `mask_employee_payload(p_payload JSONB)` (Decision #10):
```sql
mask_employee_payload(p_payload JSONB)
  └─► Replaces "national_id_encrypted" with "[REDACTED]"
  └─► Replaces "contact_info_encrypted" with "[REDACTED]"
```
As verified in acceptance test `2.D.3`, plaintext cryptographic ciphertexts are expunged prior to string serialization. The serialized payload recorded into `audit_log.old_value` and `audit_log.new_value` contains only non-sensitive metadata (employee names, roles, departments, hire dates) and the explicit redaction token `"[REDACTED]"`.

### 2.3 Role-Based Discretionary Access Control
Argus implements strict privilege separation across database roles:
1. **`hr_admin`:** Granted `SELECT, INSERT, UPDATE` on operational tables (`employees`, `salary_history`). Strictly prohibited from mutating or directly manipulating `audit_log` via explicit `REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON audit_log FROM hr_admin, PUBLIC` (all audit records append exclusively via `SECURITY DEFINER` trigger functions owned by `postgres`).
2. **`compliance_auditor`:** Granted read access solely to non-sensitive views (`v_compliance_overview`, `v_employee_directory`) and the `audit_log` table. Prohibited from reading underlying operational tables with encrypted fields or modifying any data.
3. **`postgres` (Superuser):** Restricted to database maintenance and backup procedures.

### 2.4 Regulatory Standards Alignment & Technical Control Support
Argus implements technical safeguards designed to **support organizational control objectives** rather than asserting unilateral certification:
- **SOC 2 Type II (CC6.8, CC7.2):** Supports control objectives for audit trail integrity, tamper detection, and unauthorized data modification monitoring.
- **SOX Section 404:** Supports internal accounting controls over financial reporting through an unalterable log of compensation modifications and defensive business rule triggers.
- **GDPR Article 25 (Privacy by Design) & Article 32 (Security of Processing):** Supported via field masking, encryption, and keyed HMAC-SHA256 blind indexing for queryable pseudonymization.
- **HIPAA Security Rule Scope:** Supports technical safeguards analogous to §164.312(b) (Audit Controls) on enterprise Human Resource (HR) personnel records (PII).

### 2.5 Zero-Leakage Selective Disclosure via Merkle Capsules (NOVEL-009)
In high-stakes corporate litigation or regulatory inquiries, compliance officers frequently face a dilemma: a subpoena demands cryptographic proof of a specific salary adjustment or contract change, but sharing the raw linear audit chain reveals confidential transactions belonging to unrelated personnel.
Argus resolves this through **Selective-Disclosure Merkle Capsules (`.arguscap`)**:
- Each checkpoint interval is structured as an RFC 6962 Merkle tree.
- When an evidence package is generated for sequence $s_i$, the engine extracts an $O(\log K)$ audit path containing only sibling hashes.
- External auditors or judicial third parties can verify the transaction against the dual-binding Ed25519 checkpoint signature without seeing any adjacent transaction names, roles, or compensation deltas.

## 3. Integrity Analysis (Core Security Focus)

Integrity is Argus's primary design goal. Integrity defense operates across three coordinated tiers:

### 3.1 Tier 1: In-Engine Hash Chaining & Atomic 2PL Serialization
- **Cryptographic Hash Chain:** Every committed operation $R_i$ records an `entry_hash` computed as $\text{SHA256}(S(R_i) \parallel H^{prev}_i)$. Because each entry cryptographically binds the state of the preceding entry, tampering with any record $R_j$ ($j < i$) breaks the chain pointer at $j+1$, rendering in-place tampering immediately detectable.
- **Strict Concurrency Serialization:** Race conditions and fork attacks are eliminated by acquiring an exclusive row-level lock on the `chain_state` singleton table (`SELECT id FROM chain_state WHERE id = 1 FOR UPDATE`) prior to hash generation. This guarantees a single, globally ordered transaction timeline.
- **Transactional Atomicity:** Because logging is embedded in an `AFTER` trigger executing within the caller's transaction, data updates and their audit records commit or rollback simultaneously. No unlogged mutations or phantom audit records can occur.

### 3.2 Tier 2: Business Rule Constraints
In addition to cryptographic integrity, Argus enforces relational domain integrity via defensive triggers:
1. **Salary Decrease Threshold Trigger (`trg_check_salary_decrease`):** Rejects any salary reduction greater than 30% of the employee's current salary, preventing malicious or accidental compensation destruction.
2. **Self-Modification Rejection Trigger (`trg_salary_history_no_self_mod`):** Verifies the calling actor's identity via `argus.actor_employee_id` and rejects transactions where an administrator attempts to alter their own compensation.
3. **National ID Immutability Trigger (`trg_employees_immutable_nid`):** Enforces write-once semantics on government identity numbers, blocking historical identity swapping.

### 3.3 Tier 3: Asymmetric Checkpoint Signing & External Anchoring
To defend against the "recompute-and-hide" attack—where a rogue superuser edits an audit entry and recomputes all subsequent hashes up to the current tail—Argus implements out-of-process signed checkpoints:
- Every $C$ entries (default 25 in demo; 250 in production), the standalone verifier computes a digest over the range of hashes:
  $$H_{cp} = \text{SHA256}(H_a \parallel H_{a+1} \parallel \dots \parallel H_b)$$
- The verifier signs $H_{cp}$ using an isolated **Ed25519 private key** inaccessible to the database engine.
- The signed checkpoint is committed to an external, independently governed repository (e.g., a private GitHub repository via personal access token).
- Because the superuser lacks the Ed25519 private key, they cannot forge signatures for recomputed chains.

### 3.4 Tier 4: Multi-Witness Threshold Quorum (RFC 9162) & Fork Defense (NOVEL-010)
To prevent single-point-of-trust failure in the external anchor store (such as a compromised GitHub PAT or malicious S3 bucket admin), Argus requires **heterogeneous multi-witness cosigning**:
- Checkpoints are formatted as canonical RFC 9162 Notes and submitted to three heterogeneous witnesses (AWS S3 WORM, RFC 3161 TSA, GitHub Git tree).
- A **2-of-3 threshold quorum** must cosign the checkpoint before it is considered finalized.
- Split-view attempts—where an adversary presents divergent history branches to different parties—are detected deterministically and yield a non-repudiable `ProofOfMisbehavior`.

### 3.5 Forensic Integrity: Counterfactual Provenance Replay (NOVEL-011)
When insider fraud or data tampering is discovered, forensic investigators must measure the precise operational and financial blast radius. Argus's counterfactual replay engine simulates what the database state would be if disputed transactions had never occurred:
$$\Delta_{\text{cumulative}} = (\text{Salary}_{\text{actual}} - \text{Salary}_{\text{counterfactual}}) \times \frac{\text{tenure\_months}}{12}$$
This transitions tamper-evident auditing from passive detection to active mathematical remediation.

## 4. Availability Analysis

A security engine must not compromise database operational availability, nor should external network failures paralyze local transaction processing.

### 4.1 Non-Blocking Audited Transactions
Writing to the audit log incurs strictly local computational overhead ($\approx 0.15\text{ ms}$ for SHA-256 digest and single-row lock acquisition). No network calls, HTTP requests, or external consensus handshakes occur within the database write path. Consequently, production transaction throughput remains high ($\approx 1,200\text{ writes/sec}$ on standard hardware).

### 4.2 Verifier Decoupling & Crash Recovery
The verifier CLI (`verifier.py`) is fully decoupled from the transactional database and application server:
- Verification operates with **read-only keyset pagination**, acquiring zero shared or exclusive table locks on production tables. Primary applications continue servicing users during verification scans.
- If the verifier process crashes mid-scan, it leaves zero dangling database state or lock artifacts. Re-running the CLI resumes verification immediately.

### 4.3 Bounded Degradation Under Network Partition
If the external anchor store (e.g., GitHub API) suffers an outage or network partition:
- PostgreSQL transactions continue committing normally without latency penalty.
- Local audit logging and local checkpoint creation continue uninterrupted.
- Detection capability for the recompute-and-hide attack is temporarily degraded to local verification until external connectivity resumes.
- Upon reconnection, `AnchorStore.push()` automatically flushes all pending local checkpoints in a single synchronization pass, restoring full external non-repudiation.
