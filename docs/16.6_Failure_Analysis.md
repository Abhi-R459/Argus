# Section 16.6 — Failure Mode Analysis

## 1. Overview & Resilience Matrix

In high-assurance database architectures, cryptographic defenses must not impair relational reliability, nor may relational faults corrupt cryptographic chain integrity. Argus explicitly analyzes, models, and mitigates six distinct failure scenarios:

| Failure Mode | Failure Point | System Behavior & Invariant Defense | Recovery Mechanism |
|---|---|---|---|
| **1. Server Crash / Power Loss** | Mid-transaction during DML or trigger | Atomic rollback via PostgreSQL WAL engine; no partial log entries | Automatic PostgreSQL crash recovery at restart |
| **2. Transaction Rollback** | Constraint violation or business rule rejection | Entire transaction aborts; sequence ID and chain state do not advance | Clean rollback; zero phantom records or sequence gaps |
| **3. Verifier Process Crash** | Mid-chain walk or checkpoint signing | Database engine unaffected; verifier exits without mutating DB | Verifier is stateless; simply re-run CLI |
| **4. High Write Concurrency** | Simultaneous inserts/updates across connections | `SELECT ... FOR UPDATE` serializes chain updates; zero race forks | Strict FIFO lock queue; deterministic linear ordering |
| **5. Anchor Store Outage** | Network partition to GitHub / external repository | Relational audit logging proceeds uninterrupted; checkpoints accumulate locally | Resilient offline queuing; retry push once connectivity restores |
| **6. Signing Key Compromise** | Verifier host breach or private key loss | Past anchored checkpoints remain immutable on external store | Ephemeral key rotation; revocation notice; re-anchor with new key |
| **7. Witness Partition / Compromise** | Network partition to 1 of 3 witnesses or rogue witness key | 2-of-3 threshold quorum continues sealing checkpoints; rogue witness detected | Quorum tolerates 1 dead witness; split views yield `ProofOfMisbehavior` |
| **8. Duplicate Leaf Malleability** | Odd leaf replication attack (CVE-2012-2459) | Odd leaves promoted without replication; domain prefix `0x00`/`0x01` | Second preimage attacks mathematically eliminated |

## 2. Detailed Failure Modes & Mitigations

### 2.1 Failure Mode 1: Server Crash & Power Outage During Mutation
- **Scenario:** A power failure or server crash occurs after the employee record is written to the table buffer but before the transaction commits, or during the execution of the `AFTER` trigger.
- **Threat to Integrity:** Risk of a "half-committed" state where the audited row exists but the audit log entry is missing, or vice versa, permanently corrupting the hash chain.
- **Argus Mitigation:**
  Because the audit entry generation (Algorithm 1) runs inside an **`AFTER` trigger within the same database transaction** (Decision #7), both the table mutation and the `audit_log` insert participate in the identical PostgreSQL Write-Ahead Log (WAL) transaction record.
  Upon reboot, PostgreSQL's standard ARIES-style WAL crash recovery scans the WAL files. If the transaction did not write a `COMMIT` record before the crash, both the table mutation and the audit row are completely undone. The `chain_state.sequence_id` and `tail_hash` never advance. No partial or orphan records can persist.

### 2.2 Failure Mode 2: Transaction Rollbacks & Business Rule Violations
- **Scenario:** An application user attempts an operation that violates a database constraint—such as attempting to drop an employee's salary by 40% (violating `trg_check_salary_decrease`), attempting to modify their own salary (`trg_salary_history_no_self_mod`), or attempting to mutate an immutable national ID (`trg_employees_immutable_nid`).
- **Threat to Integrity:** If sequence IDs were generated from an uncommitted sequence generator (like a standard PostgreSQL `CREATE SEQUENCE`), an aborted transaction would leave a gap in sequence numbers ($s_i = 5$, $s_{i+1} = 7$), which the verifier would interpret as an illicit deletion attack.
- **Argus Mitigation:**
  Argus does **not** rely on standard PostgreSQL `SEQUENCE` objects for the audit log sequence. Instead, `sequence_id` is derived directly from the singleton `chain_state` table inside the exclusive lock:
  ```sql
  SELECT sequence_id, tail_hash FROM chain_state WHERE id = 1 FOR UPDATE;
  ```
  If any trigger raises an exception (`RAISE EXCEPTION`), the entire transaction aborts. Because the lock on `chain_state` rolls back alongside the transaction, the `sequence_id` counter is restored to its exact pre-transaction value. The next successful transaction will claim the exact consecutive integer, guaranteeing that failed or aborted transactions never introduce sequence gaps into the verified chain.

### 2.3 Failure Mode 3: Verifier Process Termination Mid-Run
- **Scenario:** The standalone verification process (`verifier.py`) is abruptly terminated (e.g., via `SIGKILL`, OOM killer, or host restart) while executing `verify-chain` or `create-checkpoint`.
- **Threat to Integrity:** In-flight verification state lost; risk of corrupting database state or leaving partial checkpoints.
- **Argus Mitigation:**
  1. **Stateless Verification:** The verifier is an out-of-process, read-only consumer (Decision #5). It executes standard `SELECT` queries and acquires no exclusive table or row locks on production tables.
  2. **Idempotent Checkpoints:** When storing checkpoints via `store_checkpoint()`, the insert is guarded by `ON CONFLICT (sequence_id) DO NOTHING` or `UPDATE` (Decision #10). Re-running the verifier simply picks up from the beginning or from the latest verified checkpoint without side effects.

### 2.4 Failure Mode 4: High Write Concurrency & Lock Contention
- **Scenario:** Multiple application workers simultaneously execute salary modifications or employee updates across dozens of concurrent database connections.
- **Threat to Integrity:** Two concurrent transactions might read the same `tail_hash`, calculate identical next sequence IDs, and create a branched fork in the hash chain.
- **Argus Mitigation:**
  Every audited write must execute:
  ```sql
  SELECT tail_hash, sequence_id FROM chain_state WHERE id = 1 FOR UPDATE;
  ```
  PostgreSQL's Two-Phase Locking (2PL) engine forces all concurrent transactions wishing to append to the chain to queue up sequentially behind the currently executing transaction. Transaction $T_2$ cannot read `chain_state` until transaction $T_1$ executes `COMMIT` or `ROLLBACK`.
  - **Deadlock Freedom:** Because `chain_state` is always locked on a single, fixed primary key (`id = 1`) as the very first step of the trigger, and no circular dependencies exist between transactions, the lock acquisition order is globally uniform, mathematically precluding deadlocks on the chain lock.

### 2.5 Failure Mode 5: Anchor Store Outage or Network Partition
- **Scenario:** The external anchoring endpoint (e.g., the GitHub API or remote storage server) becomes completely unreachable due to an ISP outage, API rate-limiting, or cloud partition.
- **Threat to Integrity:** Does external network failure prevent the primary application from processing payroll or updating employee records?
- **Argus Mitigation:**
  Argus enforces strict architectural decoupling between internal transaction commits and external anchoring:
  1. **Primary Writes Never Block:** The database triggers only compute and store hashes locally within PostgreSQL. They have zero outbound network dependencies. The database continues processing transactions at full speed.
  2. **Bounded Degradation:** The verifier CLI continues generating local checkpoints in `chain_checkpoints`. The only degraded capability is the immediate off-site anchoring of the newest checkpoints.
  3. **Resilient Catch-Up:** As documented in `AnchorStore` (CRYPTO-003), checkpoints awaiting anchor synchronization are queried using `get_unanchored_checkpoints()`. As soon as network connectivity is restored, the CLI pushes all accumulated checkpoints in a single catch-up sweep.

### 2.6 Failure Mode 6: Private Signing Key Compromise or Loss
- **Scenario:** The host system storing `~/.argus/argus_private.pem` is compromised, or the key file is accidentally deleted.
- **Threat to Integrity:** Can an attacker rewrite history prior to the key compromise? Can the system recover if the key is lost?
- **Argus Mitigation:**
  1. **Forward Secrecy of Past Anchors:** Even if an attacker steals the private key at timestamp $t_{compromise}$, they cannot forge or rewrite checkpoints anchored to the external repository *prior* to $t_{compromise}$. The external repository's immutable commit history preserves the legitimate signatures created before the breach.
  2. **Key Rotation Protocol:** If a key is lost or compromised:
     - Generate a new Ed25519 keypair (`python -m db.cli.verifier keygen`).
     - Commit the new public key (`argus_public.pem`) to the external repository along with a signed key revocation statement.
     - Resume checkpoint signing from sequence $s_{current}$ using the new private key.
     - Past checkpoints remain verifiable using the archived historical public key.

### 2.7 Failure Mode 7: Multi-Witness Partition or Rogue Witness Compromise (NOVEL-010)
- **Scenario:** One of the three heterogeneous witnesses (e.g., S3 WORM, RFC 3161 TSA, or GitHub) goes offline due to cloud provider outage, or a single witness's credentials are stolen.
- **Threat to Integrity:** Can an attacker who controls a single witness sign false checkpoints? Does a single cloud outage halt checkpoint notarization?
- **Argus Mitigation:**
  1. **Threshold Quorum Resilience:** Checkpoints require an $M$-of-$N$ threshold quorum (default $2$-of-$3$). If any single witness is offline, the remaining two witnesses continue notarizing checkpoints without downtime.
  2. **Split-View / Fork Detection:** If an adversary attempts to present two different checkpoint states for the same sequence ID to different witnesses, the verifier protocol collects conflicting `CheckpointNote` objects and emits a cryptographic `ProofOfMisbehavior`, permanently exposing the fork.
  3. **Multi-Domain Independence:** By distributing witnesses across different cloud providers and protocol families (AWS S3 Object Lock, RFC 3161 PKI, Git repository), compromise of any single platform IAM root does not grant adversary quorum.

### 2.8 Failure Mode 8: Merkle Duplicate Leaf Malleability (CVE-2012-2459) & Second Preimage Attacks (NOVEL-009)
- **Scenario:** An audit block contains an odd number of transactions $K$. In naive Merkle tree implementations (such as the early Bitcoin protocol), odd leaves are duplicated to form pairs (`(L_odd, L_odd)`), allowing adversaries to forge valid inclusion proofs for duplicate synthetic entries.
- **Threat to Integrity:** An attacker crafts synthetic transactions that resolve to the same root hash.
- **Argus Mitigation:**
  1. **Odd-Leaf Promotion:** In `ArgusMerkleTree` (`merkle_tree.py`), odd leaves are promoted directly to the parent layer without duplication:
     $$N_{\text{parent}} = N_{\text{odd}}$$
     This mathematically eliminates duplicate leaf ambiguity.
  2. **RFC 6962 Domain Separation:** Leaf hashes are prefixed with `0x00` and internal parent nodes are prefixed with `0x01`. An attacker cannot present an intermediate node hash as a leaf transaction, eliminating second-preimage attacks.
  3. **Dual-Binding Checkpoints:** The checkpoint signature covers both the cumulative linear hash and the Merkle root:
     $$\text{message} = H_{cp} \parallel \text{":"} \parallel \text{merkle\_root}$$
     Neither the linear chain nor the Merkle tree can be substituted independently.
