# Section 16.4 — Formal Algorithm Specification

## 1. Mathematical Foundations & Serialization Contract

Let $\mathcal{D}$ denote the relational database state, and let $\mathcal{T} = \{\text{employees}, \text{salary\_history}\}$ represent the set of security-audited relational tables. Every data manipulation operation (DML) $op \in \{\text{INSERT}, \text{UPDATE}, \text{DELETE}\}$ executed on $T \in \mathcal{T}$ triggers an atomic audit logging procedure within the caller's transaction.

### 1.1 Record Tuple Definition
An audit log event is defined as a tuple:
$$R_i = \langle s_i, u_i, a_i, t_i, r_i, v^{old}_i, v^{new}_i, \tau_i, H^{prev}_i, H^{curr}_i \rangle$$
where:
- $s_i \in \mathbb{N}$: Monotonically increasing sequence identifier ($s_i = s_{i-1} + 1$).
- $u_i \in \mathbb{N} \cup \{\bot\}$: Identifier of the invoking user (`actor_user_id`).
- $a_i \in \{\text{INSERT}, \text{UPDATE}, \text{DELETE}\}$: The executed operation type.
- $t_i \in \Sigma^*$: The target relation name (`table_name`).
- $r_i \in \mathbb{N}$: The primary key of the modified table row (`row_id`).
- $v^{old}_i \in \mathcal{J} \cup \{\bot\}$: JSONB representation of the pre-image, with PII fields replaced by `[REDACTED]`.
- $v^{new}_i \in \mathcal{J} \cup \{\bot\}$: JSONB representation of the post-image, with PII fields replaced by `[REDACTED]`.
- $\tau_i \in \mathbb{R}^+$: Transaction timestamp (`created_at`) formatted with ISO-8601 precision.
- $H^{prev}_i \in \{0, 1\}^{256}$: SHA-256 digest of the immediately preceding chain state ($H^{prev}_i = H^{curr}_{i-1}$, with $H^{prev}_1 = 0^{64}$).
- $H^{curr}_i \in \{0, 1\}^{256}$: The computed cryptographic digest of entry $R_i$.

### 1.2 Serialization Bijection Contract (SETUP-002)
To guarantee strict deterministic reproducibility across heterogeneous runtime environments (PostgreSQL `pgcrypto` C-runtime and Python standard libraries), the canonical byte serialization $S(R_i)$ is defined as the pipe-delimited UTF-8 octet string:

$$S(R_i) = s_i \parallel \text{"|"} \parallel u_i \parallel \text{"|"} \parallel a_i \parallel \text{"|"} \parallel t_i \parallel \text{"|"} \parallel r_i \parallel \text{"|"} \parallel \hat{v}^{old}_i \parallel \text{"|"} \parallel \hat{v}^{new}_i \parallel \text{"|"} \tau_i$$

where $\hat{v} = \text{"null"}$ if $v = \bot$, and $\hat{v} = \text{SerializeJSON}(v)$ otherwise.

The cryptographic entry digest is computed recursively as:
$$H^{curr}_i = \text{SHA256}(S(R_i) \parallel H^{prev}_i)$$

## 2. Core Security Invariants

The Argus verification engine guarantees the following invariants over the audit log relation $\mathcal{L} = \{R_1, R_2, \dots, R_N\}$:

- **Invariant 1 (Strict Monotonic Sequence):**
  $$\forall i \in \{2, \dots, N\}, \quad s_i = s_{i-1} + 1 \quad \text{and} \quad s_1 = 1$$
- **Invariant 2 (Cryptographic Hash Linkage):**
  $$\forall i \in \{2, \dots, N\}, \quad H^{prev}_i = H^{curr}_{i-1} \quad \text{and} \quad H^{prev}_1 = 0^{64}$$
- **Invariant 3 (Content Integrity):**
  $$\forall i \in \{1, \dots, N\}, \quad H^{curr}_i = \text{SHA256}(S(R_i) \parallel H^{prev}_i)$$
- **Invariant 4 (Signed Checkpoint Authenticity):**
  $$\forall C_j = \langle s^{start}_j, s^{end}_j, H^{cp}_j, \sigma_j \rangle \in \mathcal{C}, \quad H^{cp}_j = \text{SHA256}\left(\bigoplus_{k=s^{start}_j}^{s^{end}_j} H^{curr}_k\right) \quad \land \quad \text{Ed25519Verify}(vk, H^{cp}_j, \sigma_j) = \text{True}$$

## 3. Algorithm 1: Audit Record Generation (Write Path Trigger)

The following algorithm executes synchronously inside PostgreSQL as an `AFTER INSERT OR UPDATE OR DELETE` trigger on audited tables.

```
Algorithm 1: In-Engine Hash-Chained Audit Record Generation
Input:
  OLD, NEW        : Record tuples of the modified table
  TG_OP           : Operation string ∈ {"INSERT", "UPDATE", "DELETE"}
  TG_TABLE_NAME   : Relation name string
Output:
  Committed row in audit_log; updated chain_state

1:  // Step 1: Concurrency serialization via exclusive row lock (Decision #2)
2:  SELECT tail_hash, sequence_id 
3:    INTO v_prev_hash, v_seq 
4:    FROM chain_state 
5:    WHERE id = 1 
6:    FOR UPDATE;
7:
8:  // Step 2: Session identity & severity resolution
9:  v_actor_user_id ← CURRENT_SETTING('argus.actor_user_id', true)::BIGINT;
10: v_severity ← assign_severity(TG_OP, TG_TABLE_NAME);
11:
12: // Step 3: Payload extraction & PII sanitization (Decision #4, #10)
13: IF TG_OP = 'INSERT' THEN
14:   v_row_id ← NEW.id;
15:   v_old_payload ← NULL;
16:   v_new_payload ← mask_employee_payload(TO_JSONB(NEW));
17: ELSIF TG_OP = 'UPDATE' THEN
18:   v_row_id ← NEW.id;
19:   v_old_payload ← mask_employee_payload(TO_JSONB(OLD));
20:   v_new_payload ← mask_employee_payload(TO_JSONB(NEW));
21: ELSE // DELETE
22:   v_row_id ← OLD.id;
23:   v_old_payload ← mask_employee_payload(TO_JSONB(OLD));
24:   v_new_payload ← NULL;
25: END IF;
26:
27: // Step 4: Advance sequence identifier
28: v_next_seq ← v_seq + 1;
29: v_created_at ← CLOCK_TIMESTAMP();
30:
31: // Step 5: Canonical serialization & SHA-256 hashing (SETUP-002, Decision #11)
32: v_serialized ← v_next_seq || '|' || COALESCE(v_actor_user_id::TEXT, 'null') || '|' ||
33:                TG_OP || '|' || TG_TABLE_NAME || '|' || v_row_id::TEXT || '|' ||
34:                COALESCE(v_old_payload::TEXT, 'null') || '|' ||
35:                COALESCE(v_new_payload::TEXT, 'null') || '|' ||
36:                TO_CHAR(v_created_at, 'YYYY-MM-DD"T"HH24:MI:OF');
37:
38: v_entry_hash ← ENCODE(DIGEST(v_serialized || v_prev_hash, 'sha256'), 'hex');
39:
40: // Step 6: Append-only insert into audit_log
41: INSERT INTO audit_log (
42:   sequence_id, actor_user_id, action, table_name, row_id,
43:   old_value, new_value, severity, entry_hash, previous_hash, created_at
44: ) VALUES (
45:   v_next_seq, v_actor_user_id, TG_OP, TG_TABLE_NAME, v_row_id,
46:   v_old_payload, v_new_payload, v_severity, v_entry_hash, v_prev_hash, v_created_at
47: );
48:
49: // Step 7: Update singleton state tail
50: UPDATE chain_state 
51:   SET tail_hash = v_entry_hash, sequence_id = v_next_seq 
52:   WHERE id = 1;
53:
54: RETURN NULL; // AFTER trigger completion
```

## 4. Algorithm 2: Sequential Hash Chain Verification

Algorithm 2 is implemented in `db.cli.hash_verifier` and executed by the standalone verifier CLI. It walks the audit log using keyset pagination to maintain $O(1)$ memory consumption.

```
Algorithm 2: Keyset-Paginated Sequential Chain Walk
Input:
  conn       : Active database connection
  start_seq  : Integer starting boundary (default 0)
  page_size  : Batch limit for keyset pagination (default 500)
Output:
  VerificationResult(is_valid, total_entries, mismatches, gaps, orphans)

1:  v_last_hash ← (start_seq = 0) ? Repeat('0', 64) : FetchEntryHash(conn, start_seq);
2:  v_expected_seq ← start_seq + 1;
3:  mismatches ← ∅; gaps ← ∅; orphans ← ∅; total ← 0;
4:  v_cursor_seq ← start_seq;
5:
6:  LOOP
7:    // Keyset pagination: index scan on idx_audit_log_seq_time (Decision #9)
8:    batch ← Query("SELECT * FROM audit_log WHERE sequence_id > %s ORDER BY sequence_id LIMIT %s", 
9:                  v_cursor_seq, page_size);
10:   IF batch is EMPTY THEN BREAK;
11:
12:   FOR EACH row IN batch DO
13:     total ← total + 1;
14:     
15:     // Check Invariant 1 (No sequence gaps)
16:     IF row.sequence_id ≠ v_expected_seq THEN
17:       gaps ← gaps ∪ {(row.sequence_id, v_expected_seq)};
18:     END IF;
19:
20:     // Check Invariant 2 (No orphaned hash pointers)
21:     IF row.previous_hash ≠ v_last_hash THEN
22:       orphans ← orphans ∪ {(row.sequence_id, row.previous_hash, v_last_hash)};
23:     END IF;
24:
25:     // Check Invariant 3 (Content integrity & recomputation)
26:     recomputed_hash ← RecomputeHash(row, row.previous_hash);
27:     IF recomputed_hash ≠ row.entry_hash THEN
28:       mismatches ← mismatches ∪ {(row.sequence_id, row.entry_hash, recomputed_hash)};
29:     END IF;
30:
31:     v_last_hash ← row.entry_hash;
32:     v_expected_seq ← row.sequence_id + 1;
33:     v_cursor_seq ← row.sequence_id;
34:   END FOR;
35: END LOOP;
36:
37: is_valid ← (mismatches = ∅ ∧ gaps = ∅ ∧ orphans = ∅);
38: RETURN VerificationResult(is_valid, total, mismatches, gaps, orphans, v_last_hash, v_cursor_seq);
```

## 5. Algorithm 3: Parallel Checkpoint Verification Engine

Algorithm 3 is implemented in `db.cli.verifier` (`--parallel`) and utilizes `concurrent.futures.ProcessPoolExecutor` to distribute chain segments across $P$ CPU cores while preserving total chain continuity.

```
Algorithm 3: Partitioned Parallel Verification with Continuity Reconciliation
Input:
  db_url      : PostgreSQL connection URI
  workers     : Number of concurrent worker processes P
  start_seq   : Starting boundary sequence ID
Output:
  Unified VerificationResult

1:  // Step 1: Retrieve all signed checkpoints to determine segment boundaries
2:  checkpoints ← FetchAllCheckpoints(db_url);
3:  IF checkpoints is EMPTY THEN
4:    RETURN SequentialVerify(db_url, start_seq);
5:  END IF;
6:
7:  // Step 2: Build disjoint segment intervals
8:  segments ← [];
9:  prev_boundary ← start_seq;
10: FOR EACH cp IN checkpoints DO
11:   segments.append((prev_boundary, cp.sequence_id));
12:   prev_boundary ← cp.sequence_id;
13: END FOR;
14: segments.append((prev_boundary, NULL)); // Final open-ended segment to chain tail
15:
16: // Step 3: Concurrent worker dispatch (Decision #15)
17: futures ← [];
18: executor ← ProcessPoolExecutor(max_workers = workers);
19: FOR EACH (seg_start, seg_end) IN segments DO
20:   futures.append(executor.submit(VerifySegmentWorker, db_url, seg_start, seg_end));
21: END FOR;
22:
23: segment_results ← [f.result() FOR f IN futures SORTED BY seg_start];
24:
25: // Step 4: Cross-segment boundary continuity verification
26: cross_orphans ← ∅;
27: FOR idx FROM 1 TO LENGTH(segment_results) - 1 DO
28:   prev_res ← segment_results[idx - 1];
29:   curr_res ← segment_results[idx];
30:   
31:   IF prev_res.last_sequence_id is NOT NULL AND curr_res.total_entries > 0 THEN
32:     first_row ← QueryFirstRowOfSegment(db_url, curr_res.start_seq);
33:     IF first_row.previous_hash ≠ prev_res.last_computed_hash THEN
34:       cross_orphans ← cross_orphans ∪ {(first_row.sequence_id, first_row.previous_hash, prev_res.last_computed_hash)};
35:     END IF;
36:   END IF;
37: END FOR;
38:
39: // Step 5: Merge anomalies and report
40: merged_result ← MergeResults(segment_results);
41: merged_result.orphans ← merged_result.orphans ∪ cross_orphans;
42: merged_result.is_valid ← (merged_result.mismatches = ∅ ∧ merged_result.gaps = ∅ ∧ merged_result.orphans = ∅);
43:
44: RETURN merged_result;
```

## 6. Algorithm 4: Counterfactual "What-If" Provenance Replay (NOVEL-011)

Algorithm 4 is implemented in `db.cli.counterfactual` and exposed via `POST /api/audit-logs/counterfactual`. It walks an entity's chronological audit log, filters out contested sequence IDs, merges state deltas in-memory, and calculates the blast radius metrics without mutating database state.

```
Algorithm 4: Counterfactual Provenance Replay & Blast Radius Quantification
Input:
  conn           : Active database connection
  employee_id    : Entity identifier to simulate
  skip_seq_ids   : Set of sequence IDs to hypothetically excise {s_1, s_2, ...}
  as_of_ts       : Temporal simulation boundary (optional)
Output:
  CounterfactualResult(actual_state, counterfactual_state, blast_radius)

1:  IF skip_seq_ids is EMPTY THEN
2:    RAISE ValueError("skip_seq_ids must not be empty");
3:  END IF;
4:
5:  // Step 1: Retrieve actual ground-truth state via DB-018 stored routine
6:  actual_state ← ExecuteScalar("SELECT reconstruct_employee_state(%s, %s)", employee_id, as_of_ts);
7:  IF actual_state is NULL THEN
8:    RAISE ValueError("Employee not found or no historical audit records");
9:  END IF;
10:
11: // Step 2: Fetch complete chronological audit trail for entity
12: audit_rows ← Query("SELECT sequence_id, action, old_value, new_value, created_at " ||
13:                    "FROM audit_log WHERE table_name = 'employees' AND row_id = %s " ||
14:                    "AND (%s IS NULL OR created_at <= %s) ORDER BY sequence_id ASC",
15:                    employee_id, as_of_ts, as_of_ts);
16:
17: // Step 3: In-memory counterfactual replay filtering out contested sequences
18: counterfactual_state ← {};
19: skipped_count ← 0;
20: FOR EACH row IN audit_rows DO
21:   IF row.sequence_id ∈ skip_seq_ids THEN
22:     skipped_count ← skipped_count + 1;
23:     CONTINUE; // Hypothetically suppress this mutation
24:   END IF;
25:   
26:   IF row.action = 'INSERT' THEN
27:     counterfactual_state ← DeepCopy(row.new_value);
28:   ELSIF row.action = 'UPDATE' THEN
29:     counterfactual_state ← MergeJSONB(counterfactual_state, row.new_value);
30:   ELSIF row.action = 'DELETE' THEN
31:     counterfactual_state ← NULL;
32:   END IF;
33: END FOR;
34:
35: IF skipped_count = 0 THEN
36:   RAISE ValueError("None of the specified skip_seq_ids matched the employee audit log");
37: END IF;
38:
39: // Step 4: Blast radius impact computation
40: actual_salary ← actual_state.get('salary', 0.0);
41: cf_salary ← (counterfactual_state is NOT NULL) ? counterfactual_state.get('salary', 0.0) : 0.0;
42: salary_delta_annual ← actual_salary - cf_salary;
43:
44: hire_date ← ParseDate(actual_state.get('hire_date'));
45: tenure_months ← Max(1, DateDiffInMonths(Now(), hire_date));
46: salary_delta_cumulative ← salary_delta_annual * (tenure_months / 12.0);
47:
48: blast_radius ← {
49:   "salary_overpaid_annual": salary_delta_annual,
50:   "salary_overpaid_cumulative": salary_delta_cumulative,
51:   "tenure_months": tenure_months,
52:   "role_diverged": (actual_state.get('role') ≠ (counterfactual_state ? counterfactual_state.get('role') : NULL)),
53:   "department_diverged": (actual_state.get('department_id') ≠ (counterfactual_state ? counterfactual_state.get('department_id') : NULL))
54: };
55:
56: RETURN CounterfactualResult(actual_state, counterfactual_state, blast_radius);
```

## 7. Algorithm 5: RFC 6962 Merkle Tree & Audit Path Extraction (NOVEL-009)

Algorithm 5 is implemented in `db.cli.merkle_tree` and utilized by `db.cli.capsule` and `db.cli.verify_capsule`. It implements strict domain separation, odd-leaf promotion (mitigating CVE-2012-2459), and logarithmic inclusion proof extraction.

```
Algorithm 5: Domain-Separated Merkle Tree Construction & Proof Generation
Input:
  leaf_data_list : Array of serialized audit record strings [S(R_1), ..., S(R_K)]
  target_idx     : Index of the specific leaf to prove (0 <= target_idx < K)
Output:
  (merkle_root, audit_path)

1:  IF leaf_data_list is EMPTY THEN
2:    RETURN (SHA256(""), []);
3:  END IF;
4:
5:  // Step 1: Compute leaf hashes with RFC 6962 domain separator 0x00
6:  current_level ← [];
7:  FOR EACH item IN leaf_data_list DO
8:    leaf_hash ← SHA256(0x00 || EncodeUTF8(item));
9:    current_level.append(leaf_hash);
10: END FOR;
11:
12: tree_levels ← [current_level];
13:
14: // Step 2: Build tree bottom-up with domain separator 0x01 and odd-leaf promotion
15: WHILE LENGTH(current_level) > 1 DO
16:   next_level ← [];
17:   FOR i FROM 0 TO LENGTH(current_level) - 1 STEP 2 DO
18:     left ← current_level[i];
19:     IF i + 1 < LENGTH(current_level) THEN
20:       right ← current_level[i + 1];
21:       parent ← SHA256(0x01 || HexDecode(left) || HexDecode(right));
22:     ELSE
23:       // Odd leaf promotion: promote left without duplicate-leaf malleability (CVE-2012-2459)
24:       parent ← left;
25:     END IF;
26:     next_level.append(parent);
27:   END FOR;
28:   tree_levels.append(next_level);
29:   current_level ← next_level;
30: END WHILE;
31:
32: merkle_root ← current_level[0];
33:
34: // Step 3: Extract O(log K) audit path for target leaf
35: audit_path ← [];
36: curr_idx ← target_idx;
37: FOR lvl FROM 0 TO LENGTH(tree_levels) - 2 DO
38:   level_nodes ← tree_levels[lvl];
39:   IF curr_idx % 2 = 0 THEN
40:     // Target is left sibling; sibling is on right if it exists
41:     IF curr_idx + 1 < LENGTH(level_nodes) THEN
42:       audit_path.append({"direction": "right", "hash": level_nodes[curr_idx + 1]});
43:     END IF;
44:   ELSE
45:     // Target is right sibling; sibling is on left
46:     audit_path.append({"direction": "left", "hash": level_nodes[curr_idx - 1]});
47:   END IF;
48:   curr_idx ← curr_idx / 2;
49: END FOR;
50:
51: RETURN (merkle_root, audit_path);
```

## 8. Algorithm 6: Multi-Witness Threshold Quorum & Fork Detection (NOVEL-010)

Algorithm 6 is implemented across `db.cli.witness_protocol` and `db.cli.anchor_store`. It guarantees non-repudiation and detects split-view attacks by validating heterogeneous RFC 9162 witness cosignatures.

```
Algorithm 6: Multi-Witness RFC 9162 Threshold Verification & Fork Defense
Input:
  witnessed_checkpoint : WitnessedCheckpoint(note, signatures, threshold=2)
  witness_key_registry : Map of witness_name -> Ed25519PublicKey
  historical_notes     : Set of previously witnessed CheckpointNote objects
Output:
  (is_valid, misbehavior_detected, proof_of_misbehavior)

1:  note ← witnessed_checkpoint.note;
2:  canonical_bytes ← FormatRFC9162Note(note);
3:
4:  // Step 1: Detect split-view fork attacks (Invariant: 1 root per sequence ID)
5:  FOR EACH prior_note IN historical_notes DO
6:    IF prior_note.sequence_id = note.sequence_id AND prior_note.merkle_root ≠ note.merkle_root THEN
7:      proof ← ProofOfMisbehavior(
8:        fork_sequence_id = note.sequence_id,
9:        note_a = prior_note,
10:       note_b = note,
11:       conflicting_roots = (prior_note.merkle_root, note.merkle_root),
12:       alert_level = "CRITICAL_SPLIT_VIEW_ATTACK"
13:     );
14:     RETURN (False, True, proof);
15:   END IF;
16: END FOR;
17:
18: // Step 2: Validate individual witness signatures against registry
19: valid_witnesses ← ∅;
20: FOR EACH sig IN witnessed_checkpoint.signatures DO
21:   pubkey ← witness_key_registry.get(sig.witness_name);
22:   IF pubkey is NULL THEN CONTINUE; // Unknown or unlisted witness
23: 
24:   signature_bytes ← Base64Decode(sig.signature_base64);
25:   IF Ed25519Verify(pubkey, canonical_bytes, signature_bytes) = True THEN
26:     valid_witnesses ← valid_witnesses ∪ {sig.witness_name};
27:   END IF;
28: END FOR;
29:
30: // Step 3: Enforce threshold quorum (e.g., 2-of-3)
31: quorum_satisfied ← (LENGTH(valid_witnesses) >= witnessed_checkpoint.threshold);
32:
33: RETURN (quorum_satisfied, False, NULL);
```
