# Section 16.10 — Sequencing, Pedagogy & Academic Mentorship Note

## 1. Project Chronology & Implementation Sequencing

The development of Argus was structured over an intensive 11-week academic project lifecycle divided into six phased milestones:

1. **Phase 1: Foundation (Weeks 1–2):** Joint schema and API contract freeze (`schema_contract.sql`, `api_contract.md`). Implementation of core normalized relational tables (`departments`, `roles`, `users`, `employees`, `salary_history`) and audit tables (`audit_log`, `chain_state`, `chain_checkpoints`) via Alembic migrations.
2. **Phase 2: Security Mechanisms (Weeks 3–4):** In-engine PL/pgSQL triggers (`audit_employees`, `audit_salary_history`) implementing SHA-256 hash chaining, Two-Phase Locking (`SELECT ... FOR UPDATE`), PII redaction (`mask_employee_payload`), severity mapping, and business rule constraint triggers (salary decrease limit, self-modification block).
3. **Phase 3: Verification Engine (Weeks 5–6):** Standalone Python verification CLI with keyset pagination (`chain_walker.py`), hash recomputation (`hash_verifier.py`), Ed25519 asymmetric key generation (`keygen.py`), checkpoint signing (`signer.py`), and pluggable external anchoring (`anchor_store.py`).
4. **Phase 4: Advanced Features (Weeks 7–8):** Parallel checkpoint verification engine (`--parallel`), database dump integrity verification via streaming SHA-256 hashing (`backup.py`), and SQL stored routines (`reconstruct_employee_state`, `refresh_suspicious_activity_flags`).
5. **Phase 5: Evaluation & Research (Week 9):** Full benchmark harness (`db/bench/`) evaluating write latency, verification throughput, checkpoint sweeps, and parallel scaling across 100 to 100,000 records. Authoring of formal threat model, algorithm, complexity, and failure analyses.
6. **Phase 6: Integration & Delivery (Weeks 10–11):** End-to-end integration, 6 attack demo rehearsals, publication plot generation, comparison matrix synthesis, and final research paper assembly.

## 2. Pedagogical Mapping to the DBMS Curriculum

Argus was engineered directly to demonstrate and extend the foundational principles taught in the BCSE302L Database Management Systems curriculum:

- **Relational Integrity & Normalization (BCSE302L Module 2):** Argus implements a fully normalized 3NF schema, enforcing strict foreign key constraints with cascaded referential actions, unique constraints, and check constraints (`amount > 0`, salary bands).
- **Concurrency Control & 2PL Locking (BCSE302L Module 4):** Rather than treating transactions as abstract theory, Argus applies Two-Phase Locking (2PL) pragmatically. By acquiring an exclusive row lock on `chain_state` (`SELECT ... FOR UPDATE`), the system demonstrates how strict serializability guarantees deterministic hash chain linkage without race conditions.
- **Write-Ahead Logging (WAL) & Crash Recovery (BCSE302L Module 5):** The atomicity of Argus's audit triggers relies fundamentally on PostgreSQL's WAL engine. Because data mutations and audit records commit in the same transaction, the system illustrates how ARIES-style recovery naturally prevents partial log writes.
- **Query Optimization & Indexing (BCSE302L Module 6):** Argus demonstrates the practical difference between linear $O(N)$ table scans and logarithmic $O(\log N)$ B-tree index traversals. Keyset pagination ensures memory-safe $O(1)$ stream verification, while composite indexes enable sub-millisecond historical time-travel reconstruction.

## 4. Application Layer Sequencing — API & Frontend Track (Nidhurshek)

The Application Layer track ran in deliberate parallel to the Database Core track, following a **mock-then-real integration discipline** that insulated frontend development velocity from database implementation dependencies.

### 4.1 Phase Sequencing

**Phase 1 — Backend Foundation (Weeks 2–3):**
The FastAPI skeleton was initialized first, establishing the CORS boundary, async SQLAlchemy session factory, and the two-layer RBAC bridge: Clerk JWT verification → local `users.role` lookup → PostgreSQL role-routed connection pool. This ordering was intentional — the session factory (`dependencies/db.py`) had to exist before any route handler could be written, as it is the foundational security primitive through which every database interaction flows. The `POST /api/auth/sync` endpoint synchronized Clerk identity into the local `users` table on each login, ensuring the `users.role` column — not any Clerk-provided claim — was always the sole authorization source.

**Phase 2 — Employee CRUD (Week 3):**
With the auth foundation in place, the five Employee CRUD endpoints (`GET`, `POST`, `PATCH`, `DELETE`, `POST /salary`) were implemented. A key sequencing decision here: `SET LOCAL app.user_id = <verified_user_id>` was written into every data-modifying transaction *before* the database triggers existed. This mirrored the architecture contract agreed with Abhinav — the application layer would emit the session variable; the trigger would read it. Neither side blocked the other.

**Phase 3 — Frontend Skeleton & HR Admin Dashboard (Week 4):**
React 19 + Vite were bootstrapped with TailwindCSS, Clerk React SDK, TanStack Query, and React Hook Form + Zod. The HR Admin Dashboard was fully wired against the live FastAPI backend (not mocked), since the Employee CRUD APIs were already functional. Pagination and search ran against real database queries from day one, surfacing index performance characteristics early.

**Phase 4 — Compliance Auditor Dashboard, Mocked First (Weeks 5–6):**
The Auditor Dashboard presented a dependency risk: the verification engine, chain visualization, and suspicious activity endpoints depended on Abhinav's trigger chain being active and the verifier CLI being functional. Rather than blocking, a mock service layer (`mockAuditService.ts`) was written to serve synthetic chain entries, verification results, and anchor status. The full dashboard UI — chain visualization, diff viewer, audit log table, verification control, anchor status indicator — was built and tested against these mocks. When Abhinav's triggers landed, swapping in real endpoints was a one-file change (`auditService.ts`), not a dashboard rebuild.

**Phase 5 — Advanced Panels & Evidence Export (Weeks 7–8):**
The Activity & Risk Panel, Time-Travel UI, Concurrency Lab, and `.arguspack` evidence export were built in this phase. The time-travel UI (`TimeTravelView.tsx`) was wired against a thin FastAPI wrapper (`GET /api/employees/{id}/time-travel`) that forwarded calls to Abhinav's `reconstruct_employee_state()` stored function. Because this wrapper existed before the stored function was finalized, the API contract was testable end-to-end with a stub response. The evidence export pipeline built the `.arguspack` bundle server-side in `api/services/export.py`, invoking the verification CLI subprocess to sign the bundle before download.

**Phase 6 — Deployment & Integration (Week 9+):**
FastAPI was deployed to Render Free via `api/Dockerfile` and `render.yaml`. The React SPA was deployed to Vercel via `vercel.json` with SPA routing rewrites. Neon Free (serverless PostgreSQL) received the Alembic migration chain. Clerk production keys replaced development keys. With the dev branch pull landing Abhinav's complete DB layer (migrations 001–013, full trigger suite, verifier CLI, KMS, benchmarks), all remaining mocks were scheduled for swap-out into real API calls.

### 4.2 Mock-Then-Real Integration Discipline

The mock-then-real pattern followed three rules:
1. **Contract First:** All endpoints were defined in `contracts/api_contract.md` before either side wrote code. The contract was the only interface — not the implementation.
2. **Mock at the Service Layer, Not the Component:** Mocks lived in `mockAuditService.ts`, a drop-in replacement for `auditService.ts`. Dashboard components imported the service by interface; swapping the implementation required no component changes.
3. **Record Every Mock:** Every mocked component and its required real DB action was logged in `.ai/PENDING_ABHINAV.md`, ensuring no mock was accidentally shipped to production.

### 4.3 Integration Handshake Points

Four concrete integration points were identified at contract freeze where both tracks had to converge precisely:

| Integration Point | Application Side | Database Side | Sequencing |
|---|---|---|---|
| **SET LOCAL / Trigger Attribution** | `SET LOCAL app.user_id = <id>` in every write transaction | `current_setting('app.user_id')` read inside AFTER trigger | App writes; DB reads — no runtime coupling |
| **POST /api/verify subprocess** | FastAPI spawns `db.cli.verifier` as subprocess, parses stdout | Verifier CLI outputs structured JSON result | API contract on stdout JSON shape frozen Week 1 |
| **reconstruct_employee_state()** | `GET /api/employees/{id}/time-travel` calls PostgreSQL stored function by name | SQL stored function defined in migration 009 | Function signature frozen in contract; wrapper tested with stub |
| **Evidence Export Signing** | `api/services/export.py` calls `db.cli.signer` subprocess to sign JSONL stream | `signer.py` accepts file path, writes detached `.sig` | Subprocess I/O contract frozen Week 6 |

### 4.4 Pedagogical Reflection — Application Layer

The Application Layer track demonstrated several course concepts in their practical operational context:

- **Transaction Management in Application Code (BCSE302L Module 3):** Every write request that modified an employee record or salary entry managed an explicit SQLAlchemy async transaction, including `SET LOCAL` variable emission, the DML statement, and commit/rollback discipline. This made the abstract transaction lifecycle concrete.
- **Role-Based Access Control at the Database Layer (BCSE302L Module 7):** The dual connection pool architecture (`hr_admin` pool / `compliance_auditor` pool) demonstrated that application-level permission checks are insufficient — database-level `GRANT`/`REVOKE` enforcement is the only guarantee that survives application code bugs or bypasses.
- **API Design as a Security Boundary:** The thin-wrapper pattern (`POST /api/verify`, `GET /api/time-travel`) illustrated that a well-designed API decouples the UI's interaction model from the cryptographic engine's implementation, allowing either side to evolve independently without breaking the other.
